# Deployment

## Local production build

```powershell
cd frontend
npm ci
npm run build
cd ..
$env:PYTHONPATH='backend'
.\.venv\Scripts\python.exe -m uvicorn app.main:app --host 127.0.0.1 --port 8000 --workers 1
```

Open http://127.0.0.1:8000. FastAPI serves the built frontend and API on one origin. Restart after the first frontend build if the backend was already running. Vite remains available separately for development.

## Docker

```powershell
docker compose config --quiet
docker compose up --build -d
```

Open http://127.0.0.1:8080. The image runs as a non-root user and includes the actual compact PPO checkpoint. Named volumes retain episode/budget data and models. Do not erase the budget database while enabling paid inference. `/api/health` is the container health check.

The default host binding is loopback. For public deployment, obtain authorization, choose a host, configure HTTPS through its ingress, provision persistent volumes, set `COMMITGYM_PUBLIC=true` and a strong `COMMITGYM_ACCESS_TOKEN` in the server secret configuration, and change the published binding only intentionally. Public mode without a token fails closed for all workspace routes. Enter the workspace token in Settings (session storage only); this is not a Nebius key.

Set Nebius secrets server-side, configure verified token prices, and keep the initial spending cap small. Do not put API secrets in Vite variables. `VITE_API_URL` is optional and public; if frontend/backend are hosted separately, set it at frontend build time and allow that frontend origin in `COMMITGYM_CORS`. Same-origin deployment avoids cross-origin configuration.

The backend is intentionally single-worker. The current process-local episode mutation lock is not suitable for a multi-worker or distributed deployment. Training is an explicit CLI operation, not an unbounded public endpoint.

## Release verification

Before claiming a deployment: verify health, create and run a baseline episode, inspect persisted history, verify replay, load the actual trained checkpoint, run a small shared-seed comparison, check no credentials appear in browser requests, and test auth enforcement. A container build or a local preview is not a public deployment.

No GitHub push or public publishing has been authorized or performed. See `FINAL_SPRINT.md` for actual local checks, Docker status and blockers.

The compose file mounts a named volume only for `/app/data`. Models are read-only image contents, so a rebuilt image always serves its own checkpoint and evaluation files.

## Render (prepared, not yet deployed)

`render.yaml` is a Render Blueprint for one Docker web service on the free plan. The Dockerfile listens on `$PORT` (Render injects it; local Docker defaults to 8000) and `/api/health` is the health check.

Verified locally on 2026-10-30 with the built image in a Render-like configuration (`PORT=10000`, `COMMITGYM_PUBLIC=true`, a workspace token): the SPA loaded (200), `/api/health` returned 200, `/api/episodes` without a token returned 401, baseline/PPO/mock-adapter episodes ran to completion with matching replays, the Docker health check reported healthy, and episodes persisted across a container restart.

Owner steps (each needs your own login, so none were done for you):

1. Push this repository to a GitHub repository you own (no remote is configured; the local `gh` CLI is signed in as a different account).
2. In the Render Dashboard: **New → Blueprint**, select that repository. Render reads `render.yaml`.
3. Leave `NEBIUS_API_KEY` empty for now (live inference is paused). `COMMITGYM_ACCESS_TOKEN` is generated by Render. Copy it from the service's Environment tab to share with judges; they enter it under Settings → Workspace access token.
4. For an open demo with no token, set `COMMITGYM_PUBLIC=false` and delete `COMMITGYM_ACCESS_TOKEN`. This is only acceptable while `NEBIUS_ENABLED=false`, because the API then has no paid endpoint to abuse.
5. After the deploy finishes, verify `https://<service>.onrender.com/api/health`, run one episode in the UI and press Verify replay.

Free-plan limits: no persistent disk, so SQLite history resets on each redeploy or restart. Instances spin down when idle, so the first request after idle can take about a minute. The saved checkpoint and evaluation ship in the image and are unaffected.
